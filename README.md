# 공시 캘린더

인수인계 자료를 참고해 만든 한국어 공시 업무 캘린더입니다. 화면은 GitHub Pages에서 실행하고, 개인 데이터는 Supabase Auth와 Postgres DB로 관리합니다. 기존 HTML·CSS·JavaScript 구조를 유지합니다.

- **월간 일정**: 달력과 업무 테이블을 전환합니다. 테이블에서 날짜·업무명 정렬과 완료 처리가 가능합니다.
- **연간 계획**: 기존 일정 데이터의 월별 업무 건수 차트와 월별 계획을 확인합니다.
- **업무 가이드**: 업무를 누르면 핵심 순서 3개, 준비물, 협조 부서와 참고 위치가 표시됩니다.
- **기준일 설정**: 연도별 주총일·실적발표일을 입력하면 준비 목표일이 계산됩니다.
- **개인 관리**: 날짜 지정, 일정 추가, 완료 표시, 설정 내보내기를 지원합니다.

## 일정의 의미

12월 결산을 기준으로 구성했습니다. **법정 기한을 확정하는 서비스가 아닙니다.**

날짜가 없는 원문 업무는 예상 소요일을 반영한 ‘초안’으로 달력에 미리 배치합니다. 시작일과 소요일은 업무 계획용 추정이며 원문의 확정 일정이 아닙니다. 초안은 월별로 고정되어 다시 방문해도 바뀌지 않으며, 직접 저장한 값이 우선합니다. 기본 소요일은 주말을 제외하고 공휴일·협조 대기기간은 따로 조정합니다. 5·8·11월 10일의 정기보고서 점검은 내부 준비 목표 예시이며 법정 제출기한이 아닙니다. 회사별 감사·검토 일정에 맞게 변경하세요. 제출 업무 자체는 같은 달의 ‘이번 달 챙길 일’에도 있습니다.

주총일·실적발표일은 기본값이 없습니다. 사용자가 입력한 기준일과 개인 저장 일정에는 ‘저장’을 표시하고, 상대일로 계산한 준비 일정에는 ‘예정’을 붙입니다. 주총 D−28은 공고 권장 목표, D−7은 보고서 제출·게시 목표, D+7은 후속 업무 진행상황 확인 목표입니다. 등기·배당 등의 법정 기한을 의미하지 않습니다. 준비일의 주말·공휴일은 자동 조정하지 않으므로 실제 일정에 맞춰 변경하세요.

과거 사례 날짜를 다음 연도 확정 일정으로 재사용하지 않습니다. 전자투표는 원문 상세 설명의 D−10 개시·D−1 마감 기준으로 정리했으며, 실제 서비스 안내가 우선합니다. 원문 보충 메모의 지배구조보고서 ‘6월’은 제출기한으로 쓰지 않고 4~5월 일정 확인 업무로 배치했습니다.

수시공시·지분 변동은 발생 사유에 따라 기한이 달라지므로 고정된 날짜를 자동 생성하지 않습니다. 업무 가이드에서 확인할 수 있습니다. 제출 전 [DART 공시업무 스케줄](https://dart.fss.or.kr/info/main.do?menu=420), [KIND](https://kind.krx.co.kr), [예탁결제원 증권대행](https://ta.ksd.or.kr)의 최신 안내를 확인하세요.

## 개인정보와 저장

공개용 코드에는 원문 파일, 인증정보, 계좌번호, 개인 연락처, 상세 지분 현황, 미공개 경영 수치를 넣지 않았습니다. 업무의 짧은 일반 요약과 출처명·참고 쪽수만 포함합니다. 원문 추출·검토 파일은 `.private/`에 있으며 Git에서 제외합니다.

추가 일정·기준일·날짜 변경·완료 상태는 **Supabase DB**에 로그인한 계정별로 저장합니다. 상단 방패 버튼 → ‘계정과 저장’에서 기존 Supabase 앱 계정(이메일·비밀번호)으로 로그인합니다. Supabase 관리 대시보드의 로그인 계정과는 별개입니다. 회원가입·익명 로그인을 새로 열지 않았으며 기존 프로젝트의 Auth 설정을 변경하지 않았습니다.

‘DB에 저장됨’이 표시된 데이터는 사이트를 나갔다 돌아오거나 다른 기기로 로그인해도 유지됩니다. 브라우저에는 SDK의 로그인 세션만 저장하며 업무 데이터를 새로 localStorage에 저장하지 않습니다. 로그인 전에는 기본 일정·가이드를 볼 수 있고 편집하려면 로그인해야 합니다. GitHub Pages는 정적 화면 파일을 제공하고 DB는 Supabase 서울 리전의 기존 연결 프로젝트에 있습니다.

기존 localStorage 데이터가 있는 브라우저에서는 로그인 후 ‘이 브라우저의 기존 데이터를 DB로 옮기기’ 버튼을 누릅니다. 다른 주소의 데이터는 읽을 수 없으므로 원래 사용한 사이트·브라우저에서 진행합니다. 기존 데이터와 DB가 같은 업무를 포함하면 브라우저 값을 적용하며 원본은 삭제하지 않습니다. JSON 백업·복원도 지원합니다. 복원 미리보기 후 확인 버튼을 누르면 로그인한 계정의 DB로 전송합니다.

연결 실패 시 변경은 화면 메모리에 남고 ‘DB 미저장’을 표시합니다. 재시도하거나 파일 백업 후 종료하세요. 다른 기기에서 같은 업무를 바꿨으면 덮어쓰기를 거부하고 DB를 다시 불러오도록 안내합니다. 서로 다른 업무의 변경은 항목별로 저장합니다. 화면에 복귀하거나 ‘DB 최신 내용 불러오기’를 누르면 다른 기기의 변경을 읽습니다. 실시간 공동 편집이나 오프라인 자동 저장은 제공하지 않습니다.

DB 구성은 [database/README.md](database/README.md)를 참고하세요. 공개 키와 URL은 공개 프론트엔드 설정이며, 사용자 접근 권한은 DB의 RLS로 제한합니다. 서비스 역할 키·DB 비밀번호는 코드에 포함하지 않습니다.

## 로컬 실행과 검증

정적 HTTP 서버로 제공합니다. 빌드된 Supabase SDK를 저장소에 포함하므로 사이트 실행에 npm 빌드는 필요하지 않습니다. HTTP 서버로 실행하세요.

```sh
python -m http.server 4173 --bind 127.0.0.1
npm test
```

## GitHub Pages

공개 저장소의 `master` 브랜치 루트를 Pages 원본으로 지정합니다. `.nojekyll`을 포함하며 모든 자산을 상대경로로 참조하므로 프로젝트 하위 주소에서도 동작합니다.

저장소 Settings → Pages → Deploy from a branch → `master` → `/(root)` → Save.
